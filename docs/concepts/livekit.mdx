# LiveKit: Agentic Meetings

LiveKit is the real-time media layer behind PocketPaw's group calls — voice, video, screen sharing, and composite room recording. The integration ships as a cloud router (`pocketpaw_ee.cloud.livekit`) that brokers room creation, participant tokens, and recording lifecycle. Agents can join calls as participants alongside humans; recordings land in S3 with owner-gated playback.

<Callout type="info">
**Status (2026-05-25):** IMPLEMENTED.

**Implementation PRs:** #1112 (LiveKit call management API + soul memory recall), #1186 (composite room recording with S3 output + owner-only controls)

**Workspace RFC:** none — direct implementation.

**What's live:** voice + video calls, screen sharing, camera, composite room recording to S3 with owner-only access, soul memory recall during calls.

**What's planned:** transcription + AI summaries + post-call auto-processing (issue #1184).

## What LiveKit Gives PocketPaw

The integration enables three call patterns:

| Pattern | Who joins | Why |
|---------|-----------|-----|
| **Human-only call** | Workspace members | Replace a Zoom for in-team discussions; record for absent members |
| **Human + agent call** | Members plus a meeting agent | The agent listens, can contribute, recalls soul memory for context |
| **Agent-only call** | Two or more agents | Multi-agent coordination on a shared topic, recorded for the human to review |

The substrate is LiveKit Cloud — `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` environment variables wire to a LiveKit project. The Python SDK (`livekit-api`) handles room CRUD and token minting; the meeting agent lifecycle runs in a subprocess to keep WebRTC and Deepgram out of the FastAPI event loop.

## Room Model

Rooms map deterministically to chat groups:

| Concept | Identifier | Scope |
|---------|-----------|-------|
| **Chat group** | `group_id` (workspace-scoped) | The conversation that owns the call |
| **LiveKit room** | `room_name = "group-call-" + group_id` | The active media session |
| **Egress (recording)** | `egress_id` (in-memory registry) | The composite recording job |
| **Participant identity** | `user_id` | The user's display name comes from `user.full_name` |

A `POST /api/v1/livekit/rooms` creates the room if it does not exist, or returns the existing one. Caller is checked for group membership; only group members may create a room, generate participant tokens, get room info, or end the call. Recording is **additionally** gated on workspace ownership.

## Composite Recording

PR #1186 added `RoomCompositeEgress` recording — LiveKit's server-side recording mode that composites the room into a single MP4 stream rather than recording per-participant tracks. The output:

- **Codec / quality:** H.264, 720p, MP4 container.
- **Destination:** S3, configured via the existing `S3_*` env vars (shared with the uploads module — same credentials, no separate bucket).
- **Lifecycle:** Start via `POST /api/v1/livekit/rooms/{group_id}/recording/start`; stop via `/recording/stop`; status via `GET /recording`.
- **Registry:** Active recordings live in an in-memory `_active_recordings: dict[str, str]` mapping `group_id → egress_id`.
- **File row:** When the recording stops, the service creates a `FileUpload` doc in MongoDB so the recording surfaces in the workspace's `/files` page alongside other uploads.

Recording controls are **workspace-owner only** (`_require_workspace_owner()`). The frontend shows a red `REC` indicator in the call top bar when active; the Record button itself only renders for owners.

## Frontend Pairing

The Svelte frontend lives in the paw-enterprise repo and consumes this router:

- **Call UI** — `paw-enterprise#206` wires `CallPanel.svelte` (Record button, REC indicator, participant grid) plus `call/service.ts` (start / stop / status / token helpers) and `call/store.svelte.ts` (CallSession state: `isRecording`, `recordingStartedAt`, `canRecord`).
- **Records UI** — `paw-enterprise#241` surfaces past recordings in the workspace records view; the `FileUpload` MongoDB row written on stop-recording is what the records page queries.
- **Permissions wiring** — `ChatPanel.svelte` passes `isWorkspaceOwner` as a prop to `CallPanel.svelte` so the Record button hides for non-owners.

## API Surface

All routes under `/api/v1/livekit/*` require an active enterprise license, user authentication, and group membership, except the two public guest-invite routes (validate and join). Recording routes additionally require workspace ownership.

| Method + Path | Purpose |
|---------------|---------|
| `POST /livekit/rooms` | Create or fetch the room for a group. The call-bot's token stays on the server; members get their own from `POST /livekit/token` |
| `POST /livekit/token` | Mint a participant access token. The LiveKit identity is always the caller's user id (a body `identity` is ignored) and `ttl_seconds` is clamped to 60-3600 (default 3600); display name comes from `user.full_name`. The room must be `group-call-<id>` for a group the caller belongs to in their workspace, otherwise 403 `livekit.room_forbidden` |
| `GET /livekit/rooms/{group_id}` | Room state: participant count, list, active flag (`active` is true only while someone other than the call-bot is in the room) |
| `DELETE /livekit/rooms/{group_id}` | End the call; all participants are disconnected; the bot's notes post shortly after |
| `POST /livekit/rooms/{group_id}/recording/start` | Begin composite recording to S3 (owner only) |
| `POST /livekit/rooms/{group_id}/recording/stop` | Stop recording; writes a `FileUpload` doc; returns the file id |
| `GET /livekit/rooms/{group_id}/recording` | Current recording status (mapped from LiveKit `EgressStatus` protobuf) |
| `POST /livekit/rooms/{group_id}/invite` | Create a guest invite link. An `emails` list inside the `display_name` JSON becomes the invite's server-side allow-list and is removed from `display_name` |
| `GET /livekit/invites/{token}` | Public. Validate an invite for the join page. Returns `requires_email` (bool); the allow-list itself is never returned |
| `POST /livekit/invites/{token}/join` | Public. Join as a guest with `display_name` and, when `requires_email` is true, `email` (checked trimmed and case-insensitively; otherwise 403 `meeting_invite.email_not_allowed`). A guest link never starts a call: if no one other than the call-bot is in the room, join returns 403 `meeting_invite.call_ended` |

Events fire on the realtime bus:

- `CallStarted` — on room create
- `CallEnded` — on room delete

The frontend's realtime channel subscribes to both so participant lists update without polling.

Starting a call goes through the workspace plan's daily call-time budget, whether a member starts it or a scheduled meeting auto-starts. When the budget is spent, a member gets 402 `billing.call_limit`, and a scheduled meeting that reaches its start time is marked `failed` with `raw_provider_payload.start_error = "billing.call_limit"`. Scheduling a LiveKit meeting on a group requires the scheduler to be a member of that group in the same workspace.

A guest invite link never starts a call. Guests of a scheduled meeting can join only after a member has joined the call; until then the join page gets `meeting_invite.call_ended`.

Ending a call closes every in-progress LiveKit meeting row for that room. If a scheduled meeting started while an instant call was already running in the same group, both rows end together, and the daily call budget counts the overlapping time once.

## Instant Meetings

`POST /api/v1/meetings/instant` starts a meeting right away, Google Meet style. It does not need an existing chat group: it creates one of type `meeting` with the host as owner and only member, named after the meeting title. Because the meeting has its own room, everything keyed on a room works unchanged: the LiveKit room `group-call-<room_group_id>`, the call-bot, meeting notes posted to the room's chat, the transcript sent to the KB, recording, and in-call chat.

Meeting rooms are hidden. They never show up in the room list (`GET /chat/groups`), workspace message search, unread badges, the @-mention channel picker, or the workspace room count, and only members can read them. They can't be edited or retyped through the chat API, and a mention of a non-member in a meeting room sends no notification.

Request body (both fields optional):

```json
{ "title": "Design sync", "description": "Q4 roadmap" }
```

The title defaults to `"Instant meeting"`. The response is the usual meeting object with these fields added:

| Field | Meaning |
|-------|---------|
| `code` | Meeting code in display form, `xxx-xxxx-xxx`: 10 lowercase letters, never `l`, `i` or `o`. Stored without dashes; a code lookup should strip dashes and lowercase, so both forms work |
| `link` | `<POCKETPAW_FRONTEND_BASE_URL>/m/<code>`, also stored as `join_url` |
| `room_group_id` | The hidden meeting room (also mirrored in `group_id`) |
| `host_user_id` | The member who started it |
| `access` | `"ask"` (default) or `"open"`: whether guests wait to be let in or join on their own. See [Guest Lobby](#guest-lobby) |
| `description` | Optional description |

The meeting row starts as `status: "in_progress"` with `source: "livekit"`, and there is exactly one row per meeting. The call goes through the daily call-time budget like any other call. When the plan has no call time left, the endpoint returns 402 `billing.call_limit` and neither the room nor the meeting row is created.

## Meetings for Later

`POST /api/v1/meetings` with `source: "livekit"` and no `group_id` creates a meeting without starting a call. It makes the same hidden `meeting` room as an instant meeting (host as only member) and a meeting row with a code and link. No LiveKit room exists until someone joins, so creating one uses no call time.

```json
{ "source": "livekit", "title": "Planning", "scheduled_start": "2026-10-03T09:00:00Z", "duration_minutes": 45 }
```

`title` is required. `scheduled_start` and `duration_minutes` (default 30) are optional. The row's status is `scheduled` either way. A null `scheduled_start` means the meeting has no date: no reminder or auto-start job is set for it. A dated one gets the usual reminder, auto-start and auto-end.

`POST /api/v1/meetings` with `source: "livekit"` and a chat-room `group_id` works as before (the caller must be a member of that room) and now also gets a `code` and `link`. Its `join_url` stays empty and `room_group_id` stays null; the room is in `group_id`. Recall (Zoom / Meet) meetings get no code.

### How long a link works

| Meeting | `link_expires_at` |
|---------|-------------------|
| No date (for later, and instant meetings) | 30 days after creation, pushed to 30 days after each join |
| Dated | The meeting's `scheduled_end` |

A meeting past its link expiry, or one that is `ended`, `cancelled` or `failed`, can't be joined. An undated meeting whose link expires before anyone joins is marked `ended` the next time the workspace's meetings are listed.

When everyone leaves a call, LiveKit closes the empty room after 5 minutes and the meeting stays `in_progress`; the next join starts a fresh call on the same meeting. Ending the call for everyone (`DELETE /livekit/rooms/{group_id}`) marks the meeting `ended`, and its link stops working.

## Joining by Code

`GET /api/v1/meetings/by-code/{code}` is public (no sign-in) and is what the `/m/<code>` page calls first. The code can be sent with or without dashes, in any case. It is limited to 30 lookups a minute per client IP (429 `meetings.lookup_rate_limited`). It returns exactly these fields:

```json
{
  "code": "abc-defg-hjk",
  "title": "Planning",
  "scheduled_start": null,
  "host_name": "Hana Host",
  "access": "ask",
  "status": "not_started"
}
```

`status` is `live` while someone other than the call-bot is in the call, `not_started` when nobody is, and `ended` when the meeting is ended, cancelled, failed or past its link expiry. An unknown code is 404. The response never includes ids, emails, members or room names.

`POST /api/v1/meetings/by-code/{code}/join` is for signed-in members of the meeting's workspace (the caller's active workspace). It adds the caller to the meeting room and makes sure the call is running, then returns what the call token flow needs:

```json
{ "room_group_id": "66fa…", "room_name": "group-call-66fa…" }
```

If no LiveKit room is running, the join starts one through the daily call-time budget and marks the meeting `in_progress`, and members of the room get the realtime `meeting.started` event. Joining a running call starts nothing new: there is still one room and one meeting row.

| Status | Code | When |
|--------|------|------|
| 403 | `livekit.room_forbidden` | The meeting is in another workspace, or it runs in a chat room the caller isn't a member of. A code only grants entry to a hidden meeting room, never to a chat room |
| 404 | `meeting.not_found` | Unknown code |
| 410 | `meeting.ended` | Ended, cancelled, failed or past its link expiry |
| 402 | `billing.call_limit` | No call time left today, and the call isn't running yet. The caller is not added to the room |

Meeting rooms can only be joined this way. `POST /chat/groups/{id}/join` refuses them.

`POST /livekit/rooms` on a meeting room (the call engine calls it every time a member joins a call) follows the same rules as the join above: it never adds an "Instant call" row, it restarts the call on the meeting's own row after LiveKit has closed an empty room, it returns 410 `meeting.ended` for an ended or expired meeting, and it goes through the call budget (402). For any other room it works as before. The recommended order for a code join is still `POST /meetings/by-code/{code}/join`, then the usual `POST /livekit/rooms` and `POST /livekit/token`.

## Guest Lobby

People without an account (or from another workspace) join through the meeting link by asking to be let in. Someone in the call admits or denies them. All three guest endpoints are public.

**1. Knock.** `POST /api/v1/meetings/by-code/{code}/knock`

```json
{ "name": "Gus Guest", "email": "gus@example.com" }
```

`name` is 1 to 80 characters after trimming. `email` is optional unless the meeting has a guest list, in which case it must be on the list (compared trimmed and case-insensitive, on the server). The reply:

```json
{ "knock_id": "66fb…", "secret": "Qx3…", "status": "waiting" }
```

`secret` is shown once. The guest needs it for every later call; the server keeps only a hash of it. A knock on a meeting that has nobody in the call yet is fine: it waits until someone joins or it expires.

**2. Poll.** `GET /api/v1/meetings/by-code/{code}/knocks/{knock_id}` with the secret in the `X-Knock-Secret` header (a `?secret=` query also works, but query strings end up in access logs). Poll every 2 seconds. While waiting, or after a denial:

```json
{ "status": "waiting" }
```

Once admitted, and only while a person is in the call, the reply also carries what the guest connects with:

```json
{
  "status": "admitted",
  "token": "eyJ…",
  "room_name": "group-call-66fa…",
  "identity": "guest-3f9a1c07b2d4e815",
  "livekit_url": "wss://…"
}
```

The token joins that one room, lasts an hour, and each poll returns a fresh one. The identity stays the same for the knock, and the `guest-` prefix means it can never match a member id or `call-bot`. If the call is empty (everyone left), an admitted guest gets `{ "status": "admitted" }` without a token, because LiveKit would start a new room for a token pointed at an empty one; keep polling. An admission lasts an hour, after which the knock reads `expired`.

**3. Cancel.** `DELETE /api/v1/meetings/by-code/{code}/knocks/{knock_id}` with the same secret returns `{ "status": "cancelled" }`.

A knock is `waiting`, `admitted`, `denied`, `cancelled` or `expired`. A waiting knock expires 10 minutes after it was made, or as soon as the meeting ends.

| Status | Code | When |
|--------|------|------|
| 404 | `meeting.not_found` / `meeting_knock.not_found` | Unknown code; or an unknown knock, a knock from another meeting, or a wrong or missing secret (all the same answer) |
| 410 | `meeting.ended` | Knock on a meeting that is ended, cancelled, failed or past its link expiry |
| 403 | `meeting.email_not_allowed` | The meeting has a guest list and the email isn't on it |
| 409 | `meeting.knock_decided` | Cancel after the knock was already answered or expired |
| 422 | | Name empty or over 80 characters |
| 429 | `meetings.knock_rate_limited` | Knocks: 10 a minute per client IP and 30 a minute per meeting code. Poll and cancel: 120 a minute per client IP |

**Access "open".** When the meeting's `access` is `"open"`, nobody has to decide: a knock is admitted straight away if a person is in the call, or on the guest's first poll after someone joins. The guest list still applies.

### Letting people in

Members of the meeting room (anyone who passes the usual call check for it) get realtime events keyed on the room:

| Event | Data |
|-------|------|
| `meeting.knock` | `{workspace_id, meeting_id, group_id, knock_id, name}`, sent for a new knock on an `"ask"` meeting |
| `meeting.knock_resolved` | `{workspace_id, meeting_id, group_id, knock_id, status}`, sent whenever a knock leaves `waiting` (admitted, denied, cancelled, expired), so every admit card clears |

`GET /api/v1/meetings/{id}/knocks` lists the guests still waiting, oldest first: `[{ "knock_id", "name", "email", "created_at" }]`. `email` is null when the guest gave none.

`POST /api/v1/meetings/{id}/knocks/{knock_id}/admit` and `.../deny` return `{ "knock_id", "status" }`. The caller must be a member of the meeting room and in the call at that moment, checked against LiveKit (a host looking at the meetings page but not in the call can't admit; the admit cards live in the call). When two people answer at once, one wins and the other gets 409.

| Status | Code | When |
|--------|------|------|
| 403 | `livekit.room_forbidden` | Not a member of the meeting room (list, admit, deny) |
| 403 | `meeting.not_in_call` | A member, but not in the call (admit, deny) |
| 404 | `meeting.not_found` / `meeting_knock.not_found` | Meeting not in the caller's workspace, or unknown knock |
| 409 | `meeting.knock_decided` | Already admitted, denied, cancelled or expired |
| 410 | `meeting.ended` | The meeting has ended |

### Changing access

`PATCH /api/v1/meetings/{id}` takes any of `access` (`"ask"` or `"open"`), `title` and `description`, and returns the meeting. Only the host can call it (403 `meeting.host_only`); a blank title is 422 `meeting.empty_title`. Any other field, such as `scheduled_start`, is refused with 422 rather than ignored. Members of the room get `meeting.updated`.

## Soul Memory Integration

PR #1112 wired soul memory recall into the meeting agent path. When an agent joins a call (via the subprocess agent lifecycle managed in `service.py`'s `_SubprocessAgentRef`), the agent's bootstrap pulls relevant soul memories into context:

- **Episodic** — past calls with the same participants, decisions made, action items
- **Semantic** — facts about projects / people / topics mentioned in the call group
- **Procedural** — call etiquette and any group-specific conventions

The result: an agent joining a recurring meeting with the same humans already knows the prior decisions, not just the last few minutes of transcript. This is the foundation the transcription + summary work (#1184) builds on — once transcripts land, they feed back into soul as episodic memories the agent recalls in the next call.

## What's Next

Three things land in the next cut, tracked under issue #1184:

1. **Transcription** — Deepgram (already in the subprocess deps) produces a live transcript that streams to the call UI and is persisted with the recording.
2. **AI summaries** — Post-call, a summarizer produces structured notes (decisions, action items, open questions) and posts them to the chat group thread.
3. **Auto-processing** — Action items detected in the summary route through the existing pocket actions pipeline so a meeting can produce concrete writes (a calendar event, a tracker entry) under the same Instinct + outcome model the rest of the system uses.

The recording infrastructure is the precondition: once a composite MP4 is reliably in S3, the transcript + summary jobs can run async against it without burdening the live call path.
