## Design Philosophy: Secure by Construction

Paw Print widgets are embedded on third-party customer-facing pages. This creates a cross-origin security surface that demands careful modeling. Every design decision in `models.py` reflects that context.

## Block Types and PawPrintBlock

The `PawPrintBlock` model is the render primitive. The `type` field drives rendering in widget.js with a closed set of values (text, image, list, button, form, divider). There is no `html` block type and no `script` type. This eliminates XSS injection paths at the schema level — a compromised backend or a confused agent cannot inject arbitrary HTML into a customer's browser through a widget spec.

The `_cap_list` validator enforces `MAX_ITEMS_PER_LIST = 50` on list-type blocks. Without this cap, a misconfigured agent could produce a spec with thousands of list items, causing the widget to lock the browser's rendering thread.

## PawPrintSpec

The top-level payload the widget fetches. The `_cap_blocks` validator enforces `MAX_BLOCKS_PER_SPEC = 64`. This is the budget the widget renderer works within — it prevents runaway spec generation from producing an unrenderable payload. `MAX_SPEC_BYTES = 64 * 1024` provides an additional byte-level guard at the serialization layer.

## PawPrintWidget and Access Tokens

`PawPrintWidget` holds the full widget configuration: `pocket_id`, `owner`, `name`, `spec`, `allowed_domains`, `access_token`, rate limit settings, and `event_mapping`.

The `access_token` is generated by `_gen_token()` using `secrets.token_urlsafe(32)` prefixed with `"pp_tok_"`. The prefix makes tokens recognizable in logs without exposing the secret. Tokens are "rotatable" — the store supports generating a new token and invalidating the old one, which is important if a token is accidentally exposed in a client-side log.

`_cap_domains` validates `allowed_domains` against `MAX_DOMAINS_PER_WIDGET = 20`. An uncapped list would allow widget operators to enumerate huge CORS allowlists, which the router would have to check linearly on every inbound event.

`_positive_rate` validates that `rate_limit_per_min` is a positive integer, preventing zero or negative rate limits that would either block all events or disable rate limiting entirely.

## PawPrintEventMapping

Describes how an inbound event type maps to a Fabric object: `creates` (the Fabric object type), `field_map` (a mapping from event payload keys to Fabric object fields). This is the bridge between customer interactions and the Pocket's data layer. The mapping is stored on the widget so it can be configured per-deployment without code changes.

## PawPrintEvent

One captured customer interaction. Key validators:

- `payload_size()` checks against `MAX_PAYLOAD_BYTES = 4096`. This matches the planning doc cap and prevents customers from sending arbitrarily large payloads through the widget endpoint.
- `_non_empty_type` validates that `type` is not an empty string — blank event types would make audit queries and event mapping lookups produce nonsensical results.

## Known Gaps

- `PawPrintBlock` has no `alt_text` field on image blocks, making image-only specs inaccessible.
- `PawPrintEventMapping.field_map` is typed as `dict[str, str]` with no validation that the mapped field names are valid on the target Fabric object type — a misconfigured mapping will fail at write time rather than at widget creation time.
