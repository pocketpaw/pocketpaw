## Overview

PocketPaw's reminder system lets users set reminders through natural language ("in 5 minutes call mom") rather than ISO timestamps. The scheduler handles parsing, scheduling, and delivery. The reminders API is the HTTP interface to that system, used by both the dashboard and channel adapters.

## List Reminders (`GET /reminders`)

`TestListReminders` covers two cases:

- **Empty**: Returns `{"reminders": []}`. The envelope wrapper (rather than a bare `[]`) keeps the response structure consistent with other list endpoints and allows future additions of `total` or `next_page` without a breaking change.
- **With reminders**: Each reminder in the response includes `id`, `text`, `trigger_at`, `created_at`, and `time_remaining`. The `time_remaining` field is generated by `scheduler.format_time_remaining(trigger_at)` — a human-readable string like "in 5m" or "in 1h 5m". The test uses `side_effect` to return different strings for each reminder, confirming the route calls the formatter per-entry rather than reusing a single value:

```python
sched.format_time_remaining.side_effect = ["in 5m", "in 1h 5m"]
```

## Add Reminder (`POST /reminders`)

`TestAddReminder` covers three cases:

- **Success**: Passes the full message string to `scheduler.add_reminder` and returns the created reminder with `time_remaining`. The test asserts the message is forwarded verbatim to the scheduler — no preprocessing occurs in the route layer.
- **Parse failure**: When the scheduler cannot extract a time from the message, `add_reminder` returns `None`. The route returns 400 with "parse time" in the detail. This gives the user actionable feedback ("I could not understand the time in your reminder") rather than a generic server error.
- **Empty message**: An empty string `""` returns 422 from Pydantic before the handler runs. This prevents the scheduler from receiving a blank input and potentially producing a confusing parse error.

## Delete Reminder (`DELETE /reminders/{id}`)

`TestDeleteReminder` covers two cases:

- **Success**: `scheduler.delete_reminder(id)` returns `True`; the response echoes `{"id": "abc123", "deleted": true}`. Echoing the ID allows the client to confirm which reminder was deleted, useful when the UI is optimistically removing entries.
- **Not found**: Returns `False`; the route returns 404 with "not found" in the detail. This prevents the client from treating a silent no-op as a successful deletion.

## Natural Language Parsing Boundary

The route does no time parsing itself — it delegates entirely to `scheduler.add_reminder`. This is the right architectural boundary: the route is responsible for HTTP protocol concerns (validation, status codes, response shape), and the scheduler is responsible for the domain logic of time parsing and scheduling. Tests for the parsing logic itself belong in the scheduler's own test file.

## Known Gaps

No `TODO` or `FIXME` markers are present. The tests do not cover: what happens if `get_scheduler()` raises (scheduler not initialised), reminders that have already fired (past `trigger_at`), or updating an existing reminder (there is no PATCH endpoint in the current design).
